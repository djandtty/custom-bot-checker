# Мониторинг цен на авиабилеты Aviasales → Telegram

Каждые 2 часа GitHub Actions проверяет цены на билеты туда-обратно
через [Aviasales Data API](https://support.travelpayouts.com/hc/ru/articles/203956163)
и присылает в Telegram:

- 🟢 **Старт мониторинга** — топ-5 цен при первом запуске наблюдения (или после смены его параметров);
- 📉 **Цена снизилась** — когда лучшая цена падает (правило задаёт `notify_mode`);
- 🏁 **Мониторинг завершён** — один раз, когда прошла последняя дата вылета, с минимумом за всё время;
- 🚨 сообщение об ошибке, если скрипт падает 3 запуска подряд (и ✅, когда всё починится).

Если снижения нет — бот молчит.

> ⚠️ API отдаёт **кэш** цен, найденных пользователями Aviasales за последние ~48 часов.
> Это не живой поиск: вариантов может не быть, а цена на сайте может отличаться.

## Быстрый старт

1. **Токен Travelpayouts.** Зарегистрируйтесь на [travelpayouts.com](https://www.travelpayouts.com/),
   токен — в разделе *Профиль → API-токен*.
2. **Бот Telegram.** Создайте бота у [@BotFather](https://t.me/BotFather) (`/newbot`) и получите токен.
   Напишите боту любое сообщение, затем откройте
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` — в ответе `"chat":{"id":...}` это ваш `chat_id`.
   Для группы: добавьте бота в группу, напишите там сообщение; id группы начинается с `-`.
3. **Секреты в GitHub:** репозиторий → *Settings → Secrets and variables → Actions →
   New repository secret*. Добавьте три секрета:

   | Имя          | Значение                    |
   |--------------|-----------------------------|
   | `TP_TOKEN`   | токен Travelpayouts         |
   | `TG_TOKEN`   | токен бота Telegram         |
   | `TG_CHAT_ID` | ваш `chat_id`               |

4. **Проверка:** *Actions → Aviasales price watch → Run workflow*, режим `test-telegram` —
   должно прийти тестовое сообщение. Затем режим `dry-run` — в логе будут тексты сообщений
   с реальными ценами, без отправки.

Дальше всё работает само по расписанию.

## Наблюдения (config.yaml)

```yaml
settings:
  notify_mode: record_low     # или any_drop — см. ниже
  top_n: 5                    # сколько вариантов в сообщении
  request_pause: 1.0          # пауза между запросами к API, секунд
  max_requests_per_watch: 60  # лимит запросов на одно наблюдение за запуск

watches:
  - name: "Стамбул ноябрь"      # уникальное имя — видно в сообщениях
    origin: MOW                 # IATA-код города или аэропорта вылета
    destination: IST
    departure_from: 2026-11-10  # диапазон дат вылета, включительно
    departure_to: 2026-11-20
    trip_days_min: 5            # длительность = дата возврата − дата вылета, в днях
    trip_days_max: 9
    direct: false               # true — только прямые рейсы туда и обратно
    max_price: null             # необязательно: уведомлять о снижении только при цене ≤ этой
```

### Как добавить наблюдение

Скопируйте блок `- name: ...` в список `watches` и поменяйте значения. Одно направление
можно добавлять несколько раз с разными датами — главное, чтобы `name` отличались.
Закоммитьте `config.yaml` (можно прямо в веб-интерфейсе GitHub: откройте файл → ✏️).
На ближайшем запуске придёт «Старт мониторинга» для нового наблюдения.

### Как поменять даты и длительность

Измените `departure_from` / `departure_to` / `trip_days_min` / `trip_days_max`
(а также `origin`, `destination`, `direct`). Бот заметит, что параметры поиска изменились
(в `state.json` хранится их хеш), начнёт наблюдение заново и пришлёт новый стартовый топ.
Минимум за всё время при этом тоже начинается заново.

`max_price` и `name` в хеш не входят: смена `max_price` не вызывает повторного старта,
а переименование создаёт **новое** наблюдение (старое состояние остаётся в `state.json`
под прежним именем, его можно удалить через `--reset`).

При старте конфиг проверяется; при ошибке (перепутаны даты, `trip_days_min > trip_days_max`,
повтор `name`, неверный IATA-код, неизвестный параметр и т. п.) запуск завершится с понятным
сообщением в логе, а после 3 неудачных запусков подряд придёт 🚨 в Telegram.

### notify_mode — когда присылать «Цена снизилась»

| Режим        | Уведомление, если лучшая цена ниже…                       |
|--------------|-----------------------------------------------------------|
| `record_low` | …цены из **последнего уведомления** (по умолчанию)        |
| `any_drop`   | …цены на **прошлой проверке** (2 часа назад)              |

Пример: старт 20 000 ₽ → выросла до 25 000 → упала до 22 000.
`record_low` промолчит (22 000 не ниже 20 000), `any_drop` сообщит о снижении 25 000 → 22 000.
В обоих режимах одна и та же цена повторно не присылается.

Если задан `max_price`, о снижении сообщается только при цене ≤ `max_price`.
Стартовое сообщение приходит всегда — чтобы было видно текущий уровень цен.

Если в кэше нет ни одного подходящего варианта, бот ничего не шлёт (запись всё равно
попадает в лог и в `history.csv` с пустой ценой). Стартовое сообщение придёт при первом
запуске, на котором варианты появятся.

## Ручной запуск и режимы

*Actions → Aviasales price watch → Run workflow*:

| Режим                | Что делает                                                                  |
|----------------------|-----------------------------------------------------------------------------|
| `normal`             | обычная проверка, как по расписанию; коммитит `state.json` и `history.csv`   |
| `dry-run`            | всё то же, но сообщения печатаются в лог; состояние не меняется             |
| `test-telegram`      | отправляет тестовое сообщение                                               |
| `compare-strategies` | сравнивает стратегии запросов на реальном API (таблица в логе)              |

Поле **reset_name** — сбросить состояние наблюдения (см. ниже).

Локально:

```bash
pip install -r requirements-dev.txt
export TP_TOKEN=... TG_TOKEN=... TG_CHAT_ID=...
python -m pricewatch --dry-run          # проверка без отправки и без записи состояния
python -m pricewatch --test-telegram    # тестовое сообщение
python -m pricewatch                    # обычный запуск
python -m pricewatch --compare-strategies
python -m pytest                        # тесты
```

## Сброс состояния наблюдения

Чтобы снова получить стартовый топ-5 (например, пропустили сообщение):

- в GitHub: *Run workflow*, режим `normal`, в **reset_name** — имя наблюдения
  (например, `Стамбул ноябрь`) или `ALL` для всех;
- локально: `python -m pricewatch --reset "Стамбул ноябрь"` и закоммитить `state.json`.

Сброс удаляет всё состояние наблюдения, включая минимум за всё время.
В режиме `dry-run` сброс действует только на этот запуск и не сохраняется.

## Как отключить мониторинг

- **Полностью:** *Actions → Aviasales price watch → ⋯ → Disable workflow*
  (включается там же — *Enable workflow*).
- **Одно наблюдение:** удалите или закомментируйте (`#`) его блок в `config.yaml`.
  Наблюдения с прошедшими датами отключаются сами после сообщения «Мониторинг завершён».
- **Реже/чаще:** поменяйте `cron` в `.github/workflows/watch.yml`
  (время в UTC; `17 */2 * * *` — каждые 2 часа в :17).

GitHub сам отключает расписание в репозитории без активности 60 дней. Здесь это не
проблема, пока бот коммитит состояние, но если коммитов долго не было — проверьте,
что workflow включён.

## Как это устроено

### Стратегия запросов

API принимает даты как `ГГГГ-ММ` (месяц целиком) или `ГГГГ-ММ-ДД`. Для каждого наблюдения:

1. **month** — запросы «месяц вылета × месяц возврата» для всех комбинаций месяцев,
   в которых может оказаться подходящая пара дат (для «Стамбул декабрь» это
   `2026-12/2026-12` и `2026-12/2027-01`), `limit=1000` с пагинацией по `page`.
   Затем локальная фильтрация: дата вылета в `[departure_from, departure_to]`,
   длительность в `[trip_days_min, trip_days_max]`.
2. Если подходящих вариантов меньше `top_n` — **day_month**: «конкретный день вылета ×
   месяц возврата» (11–16 запросов на наблюдение).
3. Если всё ещё мало — **pairs**: точные пары «день вылета × длительность»
   (55–66 запросов); пары дат, по которым уже есть варианты, пропускаются.

Общий лимит — `max_requests_per_watch` запросов на наблюдение за запуск,
между запросами пауза `request_pause`. При 429 бот ждёт (`Retry-After` или 5 и 15 с)
и повторяет до 2 раз; сетевые ошибки и 5xx — тоже до 2 повторов; 401 — сразу ошибка
(остальные наблюдения пропускаются, чтобы не тратить запросы).

### Отбор вариантов

Из ответов отбрасываются просроченные цены (`expires_at` в прошлом), варианты с датой
вылета в прошлом и не подходящие по датам/длительности (при `direct: true` — ещё и
с пересадками). Дубли — одинаковые даты + авиакомпания + номер рейса — схлопываются
до самого дешёвого. Сортировка по цене, в сообщение идут `top_n` лучших.
Названия авиакомпаний берутся из справочника Travelpayouts (если он недоступен — IATA-коды).

### Файлы

| Файл                          | Назначение                                                         |
|-------------------------------|--------------------------------------------------------------------|
| `config.yaml`                 | наблюдения и настройки                                             |
| `state.json`                  | состояние по `name`: хеш параметров, последняя уведомлённая цена, цена прошлой проверки, минимум за всё время (с датами), время проверки; счётчик падений |
| `history.csv`                 | `checked_at, name, min_price, departure_date, return_date, airline, offers_found` — одна строка на наблюдение за запуск |
| `pricewatch/`                 | код: `config` (валидация), `api` (HTTP), `fetch` (стратегии), `offers` (фильтры), `decide` (логика уведомлений), `messages`, `telegram`, `state`, `runner` |
| `.github/workflows/watch.yml` | расписание, ручной запуск, коммит состояния                        |

`state.json` и `history.csv` создаются при первом обычном запуске и коммитятся ботом
(только если изменились). Сообщение отмечается как отправленное только после ответа
Telegram 200 — если отправка упала, на следующем запуске бот попробует снова.

### Безопасность

Токены берутся только из переменных окружения (секреты GitHub). Они не выводятся
в лог: ошибки сети Telegram логируются без URL (в нём токен), а значения секретов
дополнительно вырезаются из всех строк лога.
